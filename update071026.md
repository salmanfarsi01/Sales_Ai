## 2. Group 1: State Binding & Decision Integrity (Points 1–5)

### Point 1: Complete Decision Binding
- **Changes**: In [copilot/core_decision_manager.py](file:///c:/dev/Sales_Ai/copilot/core_decision_manager.py), cache keys were upgraded from single version numbers to a strict 4-tuple: `(call_sid, source_state_version, turn_id, source_event_id)`.
- **Validation**: Frontend and replay consumers validate that the decision's bound `call_sid`, `turn_id`, and `source_event_id` match the state snapshot before rendering. Different calls or multiple turns sharing the same state version can never collide.

### Point 2: Runtime Isolation & Single Snapshot
- **Changes**: Removed all global fallback singletons (`default_call`). Every invocation of [ConversationStateManager](file:///c:/dev/Sales_Ai/copilot/conversation_state_manager.py) constructs an independent, isolated manager instance.
- **Snapshot Integrity**: [CoreDecisionManager.evaluate_state](file:///c:/dev/Sales_Ai/copilot/core_decision_manager.py) evaluates against a deep-copied, immutable snapshot. Evidence Considered references the exact snapshot version used to generate the decision.

### Point 3: Missing Decisions Preservation
- **Changes**: When a turn produces no decision or encounters a cache miss, the system emits `None` or an explicit `PENDING_NO_DECISION_RECORDED` status.
- **Validation**: Missing decisions are never silently promoted to a later turn's decision or a final call conversion.

### Point 4: Remaining State Consistency (Spouse & Stakeholders)
- **Changes**:
  - Reconciled the early assumption of `sole_decision_maker` when Turn 10 introduces the spouse ("Actually, my wife would really need to be part of this conversation").
  - Added stakeholder tracking in [ConversationStateManager](file:///c:/dev/Sales_Ai/copilot/conversation_state_manager.py), flagging the spouse as an active decision participant.
  - Reconciled Turn 18 confirmed conversion event participants: `participants = ["client", "spouse", "salesperson"]`.

### Point 5: Evidence & Wording Accuracy
- **Changes**:
  - Unmeasured trust (default 0.50 score) is explicitly tagged as `unmeasured_default` and cannot be presented as "established healthy trust". An unmeasured trust penalty is applied during confidence scoring.
  - Gated teleprompter prompts in [copilot/llm_gateway.py](file:///c:/dev/Sales_Ai/copilot/llm_gateway.py): prompts never state "I've booked this on the calendar" unless a verified calendar write or scheduling agreement event has completed.

## 3. Group 2: Core Intelligence & Strategic Decision Engine (Points 6–14)

### Point 6: Split Action, Posture & Push Strength
- **Changes**: Refactored [StrategicDecision](file:///c:/dev/Sales_Ai/copilot/conversation_state_models.py) to independently output:
  - `action`: Specific execution technique (`acknowledge`, `clarify`, `mirror`, `educate`, `question`).
  - `strategic_posture`: Overarching stance (`protect`, `advance`, `explore`, `coordinate`).
  - `push_strength`: Pressure level (`none`, `low`, `medium`, `high`).
- **Benchmark Resolution**: Turn 18 maps to:
  `action="acknowledge"`, `strategic_posture="protect"`, `push_strength="none"`.
  Protecting an appointment carries zero sales pressure.

### Point 7: Decision-Maker Logistics vs. Genuine Risk
- **Changes**: Turn 10 absent decision-maker statement is parsed as logistical coordination (`DECISION_MAKER_ABSENT`, `COORDINATION_LOGISTICS`, `COLLABORATIVE_SCHEDULING`), mapping to posture `coordinate` and push `low`, rather than treating it as an adversarial `DE_RISK` emergency.

### Point 8: Support WAIT / HOLD / No Spoken Prompt
- **Changes**: Added prompt suppression flags. On salesperson turns (Turns 11, 13, 17) or holding states, `should_prompt=False`, and teleprompter stub outputs `[SUPPRESSED/NO PROMPT]`.

### Point 9: Primary and Secondary Strategy Discipline
- **Changes**: Enforced a strict maximum of one primary strategy and one secondary strategy. Stacking three or more tactics is prohibited. A secondary strategy is only populated if it has a distinct functional justification synergistic with the primary.

### Point 10: Confidence-Driven Action & Degradation
- **Changes**:
  - Implemented confidence floors and downgrade ladders. If overall decision confidence is <0.65, high-pressure closing actions are downgraded to cautious exploration or collaborative scheduling (`LOW_CONFIDENCE_ACTION_DOWNGRADE`).
  - Unmeasured trust receives a discount penalty, reducing composite confidence until measured signals confirm trust.

### Point 11: Relevant Evidence Filtering
- **Changes**: Filtered `evidence_considered` to include only signals that materially justified the decision (active objections, timing deltas, readiness gate state, explicit utterances). Dormant or non-contributing dimensions are pruned.

### Point 12: Object Ownership Preservation
- **Changes**: Ensured clean separation between state and decision models. Canonical state resides in `ConversationStateSnapshot`. `StrategicDecision` stores references (`source_state_version`, reason codes, action directives) without duplicating canonical state dictionaries. Verified via AST audit.

### Point 13: Preserve Strategy Across Filler Turns
- **Changes**: When a client turn contains filler or low-materiality pleasantries, the prior turn's active strategy is carried forward with provenance tagged `STRATEGY_CARRIED_FORWARD`, avoiding redundant re-generation.

### Point 14: Strategy History Anti-Repetition
- **Changes**: If an objection persists across multiple turns, [CoreDecisionManager](file:///c:/dev/Sales_Ai/copilot/core_decision_manager.py) inspects strategy history to prevent repeating the same unsuccessful approach without new supporting evidence.

## 4. Group 3: Prospect Memory Architecture & Security Isolation (Points 15–18)

### Point 15: Memory Hierarchy and Multi-Tenant Ownership
- **Partitioning**: Strictly organized as `user_id -> prospect_id -> records`. Memory is never shared across users.
- **Side-Effect-Free Lookups**: Querying non-existent partitions returns `[]` without creating dictionary keys (`len(_storage) == 0`).
- **Normalization**:
  - `user_id`: Normalized to string and stripped of whitespace (`12345` -> `"12345"`).
  - `prospect_id`: Simplified NANP normalization handles phone formatting variants (`+1-555-0100`, `+15550100`, `(555) 0100` -> `+15550100`).
- **Security Invariant**: User B calling the same phone number as User A receives zero memory and zero exposure.

### Point 16: Required Record Schema
Every persistent memory record in [ProspectMemoryRecord](file:///c:/dev/Sales_Ai/copilot/prospect_memory.py#L100) enforces all six mandatory fields:
1. `user_id`: Mandatory non-empty string.
2. `prospect_id`: Mandatory non-empty string.
3. `source_call_sid`: Mandatory originating call identifier.
4. `timestamp`: Mandatory positive integer (`ge=1`). Missing or non-positive timestamps raise validation errors.
5. `memory_type`: Categorical identifier (`contact_preference`, `timeline`, `fact`, `objection`, `constraint`).
6. `source_turn_id` / `source_event_id`: Pydantic model validator requires in-call records to specify at least one of `source_turn_id` or `source_event_id`. Missing both is rejected.

### Point 17: Five Verified Runtime Situations
1. **Same user + same prospect**: Eligible memory loads under policy into `loaded_prospect_memory` with complete provenance. Active call `facts` remains clean (`facts == []`).
2. **New call + same user + same prospect**: Fresh `ConversationState` constructed with its own `call_sid`. Historical memory loaded separately with original call provenance.
3. **Different user + same prospect/phone**: Zero retrieval, zero exposure. User B retrieves empty list.
4. **New simulation/test**: Memory is off by default (`load_prospect_memory=False`). If requested without `user_id`, fails closed.
5. **Any current call**: `ConversationState` stays strictly isolated to its own `call_sid`. Writes made during Call 1 appear solely in the memory store, never in Call 2's active conversation state.

### Point 18: Structural Guard Against Shared/Team Memory
- **Legacy Fallback Elimination**: Removed all unscoped fallbacks in `_load_prospect_memory()`. If `user_id` is omitted, the loader immediately fails closed.
- **Shared Memory Guard**: `ProspectMemoryStore.get_shared_team_memories()` raises `NotImplementedError`.
- **AST Audit**: Proves that every retrieval method in `ProspectMemoryStore` mandates `user_id` in its formal argument list.
- **Test-Gating of `clear()`**: `ProspectMemoryStore.clear()` is protected by an environment check and raises `RuntimeError` if invoked outside test contexts.

## 5. Policy Limits on Historical Memory & Security Rules

### Definition of "Eligible" Memory
> **Eligible Memory**: Memory belonging to the identical `user_id` and `prospect_id`, loaded only when `load_prospect_memory=True` is explicitly passed by the backend, with contact preferences applied under the in-call supersession rule. There is no consent flag or recency limit.

### Three Policy Invariants
1. **Rule (a) Non-Compliance Separation**: Historical timeline and fact memories load exclusively into `loaded_prospect_memory` and never alter `contact_compliance` or current call `facts`.
2. **Rule (b) Provenance Tagging**: Applied historical contact boundaries are tagged with `is_historical=True`, originating `source_call_sid`, and `source_turn_id`.
3. **Rule (c) In-Call Supersession (Fail-Safe)**: A newer in-call preference on a channel suppresses all historical preferences on that channel, even ones with a different meaning. This fails safe by prioritizing live prospect utterances over historical assumptions.

## 6. Handoff Contract: AI Layer vs. Backend Responsibilities

```
+---------------------------------------------------------------------------------------------------+
| AI LAYER GUARANTEES                                                                               |
+---------------------------------------------------------------------------------------------------+
| 1. Partitioned Storage: Memory is partitioned strictly by user_id then prospect_id.              |
| 2. Fail-Closed Retrieval: Any retrieval path invoked without a valid user_id fails closed (0 mem).|
| 3. Scoped Write Binding: Writes bind strictly to the manager's user_id, supplied by the backend.  |
| 4. No Shared Paths: Zero shared, team, or universal memory retrieval paths exist in the engine.   |
+---------------------------------------------------------------------------------------------------+
```

```
+---------------------------------------------------------------------------------------------------+
| BACKEND REQUIREMENTS (Must provide before live multi-user use)                                     |
+---------------------------------------------------------------------------------------------------+
| 1. Authenticated User ID: user_id must come strictly from the authenticated session, not payloads|
| 2. Canonical Phone Parsing: Full E.164 phone normalizer (area codes, international carrier format)|
| 3. Reserved-ID Rejection: Reject pseudo-user IDs ('legacy_migrated_user') at the API gateway     |
| 4. Concurrent Write Store: Row-level database locking or ACID store replacing atomic JSON write   |
| 5. Status Code Mapping: Map fail-closed signals to call metadata (e.g. MEMORY_ACCESS_DENIED)     |
| 6. Test Helper Cleanup: Remove test_only_confirmation or move clear() entirely into test helpers  |
+---------------------------------------------------------------------------------------------------+
```
